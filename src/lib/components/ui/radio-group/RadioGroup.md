# RadioGroup — port notes

Deliberate departures from the reference's published prop contract, and the
component-specific decisions behind them. The reference `.d.ts` is authoritative
for prop names, unions and defaults; everything below overrules it on purpose.
**Do not "fix" one back.**

The rules that hold for _every_ component — the styling contract, semantic
tokens, status roles, snap-don't-extend, the no-`pill` directive, theming, the
accessibility floor and the standing port decisions — live in
`.agents/skills/tia-design-system/SKILL.md`. Read that first; this file is only
what is true of RadioGroup and `Radio` alone.

## What the size map holds

The reference's `10 | 13 | 16px` block padding and `12 | 15 | 18px` inline padding
are **written, not snapped** — every one is an exact quarter-step of Tailwind's own
`0.25rem` multiplier (`py-2.5`, `py-3.25`, `py-4`; `px-3`, `px-3.75`, `px-4.5`), the
same mechanism `px-3.25` and `size-4.25` already ship on. The dial is `16 | 20 | 24px`
and its mark `6 | 8 | 10px`, both the reference's, as absolute classes rather than a
percentage of the box — `border-2` takes 4px off the content box a percentage would
resolve against.

## What `error` paints, and what it does not

`error` paints the group's **label** and its **message** in `--destructive`, sets
`aria-invalid` on the group, and stops there. The dials, the marks, the icons, the
option labels, the descriptions and the card tiles' own borders all render exactly
as they do in a valid group — pinned by a test that renders one row both ways and
compares all four.

The rule behind it: **the red marks what `aria-invalid` marks.** The group is what
is invalid, because the thing that is wrong is that no choice has been made. No
individual option is wrong for being on offer, and a selected row must keep saying
"this is the one you picked" — the reference painted that mark red, which is the
selected signal and the error signal drawn in one colour a few pixels apart.

`--destructive` is the control-error role the whole library uses and the one step
neither theme block lifts, so the red does not change hue between canvases — that
is deliberate, and it carries the cost `Checkbox.md` sets out: `#db0000` is
**2.6:1** on `--card-background` under `.dark`, below AA for text. That cost is
accepted for the group's label and its message, the same short actionable sentence
Checkbox accepts it for. It is _not_ accepted for the options, and that asymmetry
is the point of the row in the table above: the reference's version paid it once
per row, for every row in the group, on ordinary body text.

`errorMessage` is still worth passing, and for the same reason as before: the
state reaches assistive technology through `aria-invalid` and the described
message, so a call site that passes one has not left a sighted user reading hue
alone. With the options now neutral, the message is doing more of that work than
it was — a `card` group in error and a `card` group at rest differ only in the
label's ink and the line underneath it.

The message is **one slot**, the shape Input settled — when it is showing, the
group's `description` is not rendered at all, rather than sitting above it. That
has to be true of the markup and not only of `aria-describedby`: swapping the id
while leaving both lines on screen shows a sighted user two sentences and tells a
screen reader about one of them, which is the accessibility floor's "`aria-*`
state that matches the visual state" failed in the direction no gate can catch.
Pinned by a test. An `error` with no message of its own leaves the description
standing, the same way Input's status-without-a-message leaves its helper text.

## Where the state comes from

`Radio` reads the **presentation** — `size`, `variant`, `error` — from a Svelte
context the group sets, declared in `Radio.svelte`'s module script so the parent
imports the setter from the child rather than the other way round. It reads the
**state** — selected, disabled — from the primitive instead, off the
`data-state="checked"` and `disabled` that `RadioGroup.Item` publishes, through
`group-data-[state=checked]:` and `disabled:` variants. Keeping the two apart is
deliberate: a second copy of the selected value in the context would be a second
source of truth for the thing bits-ui already owns, and the two can disagree for a
frame.
